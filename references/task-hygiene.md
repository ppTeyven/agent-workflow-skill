# 任务清单、agent 生命周期与交付纪律

> 对应用户原话：
> 「你是否有一些未完成的任务但却不确定是否要做，有可能不需要做，你逐个问我一下要不要继续做下去还是要取消这一项任务」
> 「现在你的行动又慢 token 耗得又快」/「你必须马上把 working 里这两个莫名其妙的 agent 强制关了」

---

## 1. 长任务清单：主动让用户裁剪

用户一次给出多件事时，**先列清单、给出取舍建议、让用户决定做哪些**，再动手。
不要闷头全部做完 —— 用户可能只需要其中两项，剩下的全是你自己烧的 token。

### 触发条件

| 情况 | 是否需要列清单 |
|---|---|
| ≥5 个子任务 | **必须**列，且逐项向用户确认 |
| 2~4 个子任务，且有可选项 | 列清单（可一次性给建议，不必逐条等回复） |
| 2~4 个子任务，全部是"必须" | 直接做 |
| 1 个子任务 | 直接做 |
| 用户已说"全都要 / 你随便" | 直接做，逐项简短汇报 |

### 格式

```
计划（按建议优先级）：
1. [必须] 修复 A
   为什么值得做：它是 B 的前置，不修 B 的验证不成立
   不做的后果：B 做完也验收不了，等于白做
   成本：~3 次工具调用
2. [建议] 补 B
   为什么值得做：独立可交付，用户能直接看到结果
   不做的后果：功能缺口，运行时才暴露
   成本：~5 次工具调用 + 一次看图
3. [可选] C
   为什么值得做：锦上添花
   不做的后果：基本无影响
   成本：~20 次工具调用（性价比最低，建议砍）
❓ Q1｜逐项确认：1 做 / 2 做 / 3 跳过？
➡️ 建议：做 1 和 2；3 放下一轮。
```

### 三个必答要素

每个候选项都必须写清：

| 要素 | 为什么必须有 |
|---|---|
| **为什么值得做** | 让用户判断优先级，而不是由 agent 单方面决定 |
| **不做的影响** | 让用户能**真正**做取舍 —— "没影响"和"会出问题"是完全不同的信号 |
| **成本估算** | 让用户能权衡；成本高的项即使有价值也可以延后 |

成本估算要给具体量级（工具调用次数 / 是否需要看图 / 是否需要跑测试），
不要写"工作量较大"这种没有决策价值的措辞。

### 原则

- 每一项标注 **[必须] / [建议] / [可选]**，让用户一眼看到取舍。
- 给出**依赖关系**（谁是谁的前置），让用户能自己决定砍哪条。
- 被裁掉的部分**记下来**，下次任务开头提一句"上次 X 没做，这次补上"—— 只提一次。

### 授权边界（最常踩的坑）

- **用户说"修这个"，通常只授权了那一项。** 不代表授权了同批次的其他优化项。
- 同批次里顺手发现的其他改进 → **列成候选项**让用户定，不要直接做。
- 例外：中途发现的**阻塞项**（不做后面都白做）可以直接修，修完汇报。
- 例外：用户说"全都要 / 你随便 / 不用问我" → 才可全部执行。

### 被否决的项不要复活

- 用户已否决 / 取消的项，**后续对话里不要反复复活**。
- 下次开工前提一句「上次 X 你说先不做，这次要不要捡回来？」—— 一次，不反复。
- 记录形式（可写进任务交接文档）：

```markdown
## 已取消 / 已否决（不要再主动提）
- [2026-11-05] 项 C「重写导入逻辑」—— 用户认为收益不足
- [2026-11-05] 项 D「加暗色主题」—— 用户暂时不需要
```

### 清单状态必须对用户可见

```
进度：
✅ 1 修复 A —— 已完成，看图确认阴影/材质正确
🔄 2 补 B —— 进行中
⛔ 3 C —— 已取消（你上一轮说先不做）
❌ 4 D —— 已跳过（依赖 2 完成，暂不启动）
```

每完成一项就给一次简短状态更新（做了什么、测出什么、下一步做什么），
不要攒到最后一次性汇报。

### 什么时候**不**要问

- 任务只有一项，或各项都是"必须"。
- 用户刚说过"直接全做"。
- 中途发现的问题本身是阻塞项 —— 直接修，修完汇报，不要为了一个小问题打断用户。

## 2. agent 生命周期：用完即停

### 起 agent 前的四个问题

```
1. 它的产出是什么？（一个文件？一份结论？一段代码？）
2. 这个产出我自己做要多贵？
3. 它能独立跑完吗？（需要我持续回答问题就不适合）
4. 跑完之后我能立刻结束它吗？
```

**第 1 题答不出来，就不要起。**

> 核心判据一句话：**这个 agent 产出的东西，我拿到后能直接做什么？**
> 答不上来，就别起。

### 拆分判据

只有当子任务满足**全部**条件时才并行：

- 天然独立（不共享上下文）
- 互不共享可变状态
- 合并后无交叉验证价值

否则**一个 agent 端到端做完**。

### 规则表

| 规则 | 说明 |
|---|---|
| 一个 agent 一件事 | 不要让一个 agent 同时探索三个方向 |
| 默认同步 | `run_in_background: false`；后台 agent 的结果常常用不上，却照常烧 token |
| 结果拿到就结束 | 不要留着常驻等后续追问 |
| 并发 ≤ 3 | 起 2~3 个够用；起 10 个是失控 |
| 起之前先告诉用户 | 让用户知道现在有几个 agent 在跑、各自干什么 |
| 不轮询 | 一次给足上下文，结束统一收结果 |
| 起时就要知道它是干什么的 | 不允许出现"我不知道这两个 agent 是什么" |

### 前台不要重复 agent 已经在做的调查

**已委派的工作，前台只做协调**：路由、收结果、整合。

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 让 3 个 agent 各查一遍同一个文件 | 三份重复 token，且互相矛盾 | 1 个 agent 查完，把结论交给主流程 |
| 起「探索性 agent」（无明确产出边界） | 变成"神秘的工作中"，用不上又停不掉 | 探索在前台做，或给它写死产出边界 |
| 前台和 agent 同时查同一件事 | 重复劳动 + 结果不一致 | 二选一 |

### 禁止轮询等待

**不要在"检查进度"上循环**（poll / AwaitShell / 反复读 agent 输出）——
这本身耗 token 且拖慢速度。

```
❌ 起 agent → 读一次输出 → 等待 → 读一次 → 等待 → ...
✅ 一次给足上下文让它自己跑完 → 结束时统一收结果
```

确需监控长任务时，用**一次** `AwaitShell` 等一个明确条件（如"等这个文件出现"），
不要 sleep 循环。

> 真实教训：一次会话里出现过 13 次「Continue waiting for X」+ 5 次「Wait for reload」——
> 这些全是纯开销，没有一次改变了结论。

### 及时停掉不用的 agent

- agent 起了不用要**及时停掉**，尤其是探索性 agent
  （它没有明确产出边界，最容易变成"神秘的工作中"）。
- 停止顺序：`Task` 工具 `interrupt=true` → 若被策略挡，用 UI 的 Stop All。
- 每轮结束检查：后台 agent 数 = 0，遗留 HTTP server / 临时脚本 / Blender 进程 = 0。
- 清理进程要用**白名单**（本项目端口），不要黑名单杀掉所有 python 进程。

### 不允许出现的状态

- "我不知道这两个 agent 是什么" —— 起的时候就该知道它们干什么。
- 任务结束后还有 agent 在跑 —— 用完即停。
- agent 跑出来的东西没人用 —— 起之前就该问产出。
- 前台和 agent 在做同一件事 —— 已委派就只做协调。

## 3. 交付纪律

### 交差格式

```
做了什么：一句话
验证：<命令 / 看图结论> → 结果
对照：修复前 X → 修复后 Y
截图：<路径>
没验到的：哪些、为什么；没有就写「无」
```

### 硬性要求

- **数字要给对照值**（修复前 → 修复后），单说"提升了"不算。
- **视觉类任务必须附截图**，且汇报第一句说的是"我看图确认了什么"。
- **没验证到的部分要明说**，不能默认略过。
- 临时探针脚本**用完即删**；原始 JSON 结果保留供复盘。
- 事实性声明标注来源（文件:行号 / 实测命令）。

### 禁止的交付用语

| 禁止 | 应该 |
|---|---|
| "应该没问题了" | "已看图确认 X、Y、Z 三处正确" |
| "测试都过了" | "`npm test` → 通过 42，失败 0" |
| "性能提升了" | "首帧 19.4s → 0.3s" |
| "已修复"（无证据） | 附对照值 + 截图 |
| "全部做完了"（清单里有被砍的） | "1、2 已完成；3 按你的要求取消" |

## 4. 事实性断言的查证纪律

**禁止凭记忆断言事实。** 涉及模型存在性、API 形态、版本号、价格、免费额度、地区可用性：

- 查官方文档 / 官方页面，并**附链接**。
- 记忆里的数字常常过时。
- 查不到就明确说"**未核实**"，不要用模糊措辞蒙混过去。
- 任何"当前最新 / 当前可用"的结论必须**带查证日期**。

能自己查清楚的事实不要交给用户；涉及用户的目标、偏好、成本和取舍时，才让用户决定。

## 5. 一次性探针脚本

- 放在临时目录，**用完即删**。
- 原始输出（JSON）单独留一份供复盘。
- 复杂逻辑写成 `.py` / `.mjs` 文件再跑，不要在 shell 里内联长脚本
  （PowerShell 会吃掉引号和 `$`）。
- 同一目录下 `_*.py` 临时文件数 > 20 说明失控，必须清理。

## 6. 迭代节奏

```
一轮 = 一个改动 + 一次复测 + 一次结论
```

- 一轮里只改一个变量，改完复测**同一个指标**。
- 结论要么"有效，继续"，要么"无效，换假设"。
- 连续两轮无效 → 停下来重新取证，不要在错误方向上继续微调。
- 每轮结束给用户一句简短状态（做了什么、测出什么、下一步做什么）。
