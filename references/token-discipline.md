# Token 预算与工具选择

> 原则：**每一分钱都要花在能改变结论的地方。**
> Token 消耗异常时，先做一次成本画像，而不是继续干。

---

## 1. 什么时候做成本分析

出现下列任一信号，**立即停下来分析**，不要"等做完再看"：

- 同一件事反复试了 3 次以上。
- 单次回答/单轮输出明显变长。
- 做了大量"读了但没影响结论"的操作。
- 任务已经跑了很久但结论还没收敛。

分析产出应该是**可执行建议**，不是一句"要节约 token"。

---

## 2. 成本画像

用 `scripts/budget_report.py` 分析一个会话记录（JSONL / JSON 均可）：

```
python scripts/budget_report.py --input <会话记录路径> --out report.md
```

它会输出：

- 每次工具调用的字符 / token 量估计，按类型聚合。
- 占比最高的前 N 项（**找浪费的地方就看他**）。
- "全量 dump"嫌疑项：单次输出超过阈值的工具调用。
- 重复调用嫌疑：同一工具同一参数反复出现。
- 建议清单：每条对应一个具体改法。

阈值可调：

```
python scripts/budget_report.py --input log.jsonl --out report.md \
    --top 15 --dump-threshold 20000
```

**实跑样例**（对一份 9.2MB / 9868 次工具调用的真实会话）：

| 工具 | 调用数 | 参数字符 | 输出字符 | 估算 token |
|---|---:|---:|---:|---:|
| `Write` | 961 | 2953002 | 0 | 738251 |
| `Shell` | 4031 | 1614588 | 0 | 403648 |
| `StrReplace` | 816 | 1174581 | 0 | 293646 |
| `CallDynamicTool` | 1791 | 817044 | 0 | 204262 |
| `<text>` | 6507 | 0 | 558083 | 139521 |

重复调用嫌疑（最该先修的）：

| 工具 + 参数 | 次数 |
|---|---:|
| `Shell`（Blender 批处理脚本） | 62 |
| `Read`（`agent-handbook/SKILL.md`） | 24 |
| `Shell`（`Start-Sleep -Seconds 29; echo ok`） | 13 |

最后一条尤其典型：**13 次 sleep 等待** —— 全部是纯开销，没有一次改变了结论。
对应纪律见第 4 节「不在检查进度上循环」。

## 3. 容易被忽视的 token 消耗大户

> 每一行都给出**量化方式**和**规避手段** —— 数字驱动，不靠感觉。

### 大户 1：大文件整份 Read / 宽 Grep 命中 minified bundle

- **量化**：命中处返回的是无语义长行，成本是正确读法的 **10 倍以上**。
  一次 `Grep` 命中 50 处 × 每处数 KB = 一次就吃掉几百 KB 上下文。
- **规避**：脚本切片 —— 只打印命中位置 **±300 字符**；**单次输出 ≤ 20 处命中**。
  命中 > 20 处 → 先收窄正则再跑。
- **注意**：复杂正则写成 `.py` 文件再执行，不要 `python -c` 内联
  （PowerShell 会吃掉引号与 `$`，导致正则被拆坏）。

### 大户 2：反复失败重试同一动作

- **量化**：同一工具 + 相同参数的调用次数。**≥ 3 次**即嫌疑；≥ 4 次应停。
- **规避**：**4 次失败就停**，报告两件事 —— ① 观察到的现象；
  ② 最可能的下一步。没有新证据就不重试。
- **反例**：13 次 `Start-Sleep` 等一个文件出现 —— 全部纯开销。

### 大户 3：全量日志 / 多 MB JSON 注入

- **量化**：单次工具输出 > **20,000 字符**即算全量 dump。
- **规避**：**摘要进对话（≤ 30 行），原始落文件**，只回文件路径 + 关键几行。
- **反例**：把一次探针的几百行 JSON 整个打进上下文 —— 挤占后续所有推理空间。

### 大户 4：每个 agent 都重新读一遍项目

- **量化**：agent 的 prompt 里出现大段重复的项目背景；
  或多个 agent 的输入指向同一批文件。
- **规避**：起 agent 时**给足上下文** —— 把已知结论、锚点、路径**直接写进 prompt**，
  让它不必自己重新发现；或让它**只读指定文件**。
- **判断**：如果 agent 的产出你能不看它读的那些文件就写进 prompt，那它就不需要读。

### 大户 5：截图 / frame 序列逐张读进对话

- **量化**：一次读入 N 张图 = N 倍视觉 token；一段 60 帧序列 ≈ 60 张图。
- **规避**：**只读关键帧** —— 首帧 + 末帧 + 异常帧（3 张足够）。
  连续序列产出可拖动/慢放的 `playback.html`，让人自己看，**不要逐帧进对话**。
- **注意**：录屏回放（L3）成本是截图（L1）的 1~2 个数量级 ——
  只有"必须看动态才能判定"才升级。

### 其它常见大户

| 大户 | 规避 |
|---|---|
| 一次性 dump 整个目录树 | 先列一层目录，需要再深入 |
| 已经贴给用户的截图再贴一次 | 只引用路径 |
| 读过的文件重复读 | 除非怀疑内容变了，不要重读 |
| 反复贴同一段代码 | 引用路径 + 行号 |

## 4. 工具选择决策树

### 我要读某个东西

```
是压缩产物 / bundle / 大 HTML / 大 JSON？
├─ 是 → 脚本切片（只输出命中处前后 300 字符），一次 ≤ 20 处命中
│        复杂正则写成 .py 文件再跑，别在 PowerShell 里内联
└─ 否 → 直接 Read（按需给 offset/limit，不要整文件无脑读）
```

### 我要确认一个事实（API 存在？版本号？价格？）

```
查官方文档并附链接 → 查不到就明确说"未核实"
绝不凭记忆断言
```

### 我要判断"看起来对不对"

```
静态结果       → 截图 + Read 图片亲眼看（L1）
动态行为       → 录屏 / 帧序列回放（L3）
混合           → 静态用截图，动态才录屏
```

### 我要定位性能问题

```
一次组合探针跑完：longtask 区间 + CPU self-time 热点 + GPU API 打桩 + 资源流向
不要分多轮试错
```

### 我要验证一个改动生效了

```
改一个变量 → 复测同一指标 → 给"修复前 → 修复后"对照值
视觉类改动再加一张 A/B 对比图
```

## 5. 高频浪费模式与替代

| 浪费模式 | 代价 | 替代 |
|---|---|---|
| 全文 Read 一个 3MB bundle | 上下文被一次性吃掉 | 脚本切片定位锚点 |
| 一次性 dump 整个目录树 | 大量无关路径进上下文 | 先列一层目录，需要再深入 |
| 把整个 JSON 打进上下文 | 几十万 token | 只取需要的字段，`jq` / 一行 python |
| 同一失败操作重试 5 次 | 每次都付一遍 tool token | 最多 2 次；第 3 次前重新取证 |
| 拿到截图路径就当看过 | 结论不可靠 | `Read` 图片文件 |
| 静态结果用录屏 | 帧序列进上下文，成本高 1~2 个数量级 | 截图 |
| 每个小问题开一次独立会话 | 重复读同一个大文件 | 合并成一次探针 |
| 反复贴同一段代码给用户 | 重复输出 | 引用路径 + 行号 |

## 6. 探针一次出全量结论

把要查的东西放进**一次**脚本运行，别分多轮：

```python
# 一次跑完：main-thread 阻塞 + 资源流向 + 关键 API 计数
# 不要分成三次运行
```

判断依据：**如果第二次运行的输入是第一次输出的子集，就是浪费** —— 应该合并。

---

## 7. 上下文里已经有的东西不要再取

- 读过的文件不要重复读，除非怀疑内容变了。
- 已经贴给用户的截图不用再贴一次。
- 已经确认过的事实不要在后续轮次重新论证。

---

## 8. 报告口径

汇报 token / 成本相关结论时给具体数：

```
本轮开销：读文件 3 次（合计 42 KB）、截图 2 次（0.9 MB）、探针 1 次
主要消耗：全量读取 bundle 一次（2.8 MB）→ 改为脚本切片后降到 8 KB
```

不要写"这次比较费 token"。
